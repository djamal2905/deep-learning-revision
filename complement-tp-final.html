1. BERT, ce qu'il faut savoir du document fourni EXAMINE DIRECTEMENT

Digeste fidele de preparation_bert.pdf (Yamane, 28/10/2026). Le TP porte sur ce document precisement, rien de plus n'est requis.

Pourquoi un encodeur seul suffit

Pour la traduction (vue en cours), un encodeur transforme la phrase source en vecteurs, et un decodeur produit la traduction mot a mot. Pour classifier un texte, la sortie est une seule etiquette (pas une phrase) : pas besoin de decodeur. BERT est un tel encodeur, et il est pre-entraine.

1. Ce qu'est BERT

Empilement de couches d'encodeur Transformer (self-attention + feed-forward), sans decodeur. "Bidirectionnel" = le vecteur d'un token depend des mots a sa gauche et a sa droite (contrairement a un decodeur causal/GPT).

2. Entree

  • Texte decoupe en sous-mots (tokenisation WordPiece), chaque token remplace par son indice.
  • [CLS] place au debut de chaque entree ; [SEP] marque la fin d'une phrase (ou la separation entre deux phrases).
  • Embedding d'un token = embedding de token + embedding de position (somme).
  • Dans un mini-batch, les phrases sont paddees a la meme longueur. Un masque d'attention (1 = vrai token, 0 = padding) est fourni : tout poids d'attention sur une position de padding est mis a 0, donc les vecteurs des vrais tokens ne dependent pas de la quantite de padding ajoutee.

3. Sortie

BERT retourne un vecteur latent par token (embedding contextuel), autant de vecteurs que de tokens en entree. Chaque vecteur est calcule par attention sur tous les tokens de l'entree. En particulier, le vecteur a la position de [CLS] peut resumer toute l'entree.

4. Utiliser BERT pour la classification

Une couche lineaire est ajoutee sur le vecteur [CLS] pour produire les scores de classe. Le fine-tuning = entrainer ensuite sur les donnees labellisees de la tache, en partant des poids appris au pre-entrainement.

VarianteCe qui est entraineCompromis

Encodeur gelep.requires_grad = False sur l'encodeur ; seule la couche lineaire entrainemoins cher, mais ne peut pas adapter ses vecteurs a la tache ⇒ accuracy generalement plus basse

5. Pre-entrainement

Avant toute tache, BERT est entraine sur une tres grande quantite de texte non labellise (livres + Wikipedia anglais) avec deux taches auto-supervisees :

  • masked language modelling : 15% des tokens sont caches, le modele doit les predire a partir du contexte ;
  • next-sentence prediction : etant donnes deux segments A et B, predire si B suit vraiment A dans le texte original ; utilise le vecteur de [CLS].

Aucun label humain requis (le texte fournit lui-meme les reponses) ⇒ l'encodeur a appris des connaissances generales sur la langue avant de voir un seul exemple labellise de la tache. Consequence : un encodeur pre-entraine a generalement besoin de beaucoup moins d'exemples labellises qu'une meme architecture entrainee from scratch. L'avantage est maximal quand les donnees labellisees sont rares, et diminue quand elles deviennent abondantes (un modele from scratch peut alors apprendre davantage des labels eux-memes).

Angle d'examen probable : comparer BERT (encodeur seul, bidirectionnel, comprehension) vs GPT (decodeur seul, masquage causal, generation) vs le Transformer complet encodeur-decodeur vu en cours pour la traduction. Savoir justifier pourquoi pas de decodeur pour une tache de classification (sortie = une etiquette, pas une sequence).

Architecture (Exercice 3), LSTM

from torch import nn

class LSTMNetwork(nn.Module):
    def __init__(self, n_channels, n_classes, n_hidden=100):
        super().__init__()
        self.lstm = nn.LSTM(input_size=n_channels, hidden_size=n_hidden, batch_first=True)
        self.linear = nn.Linear(n_hidden, n_classes)
        self.loss_fn_mean = nn.CrossEntropyLoss(reduction='mean')
        self.loss_fn_sum  = nn.CrossEntropyLoss(reduction='sum')

    def forward(self, x):
        # x: (batch, 128, 9). output: (batch, 128, hidden) ; h_n: (1, batch, hidden)
        output, (h_n, c_n) = self.lstm(x)
        last_hidden = h_n[-1]              # derniere couche, dernier pas de temps : (batch, hidden)
        return self.linear(last_hidden)

    def configure_optimizers(self):
        return torch.optim.Adam(self.parameters())

    def training_step(self, batch):
        X, y = batch
        pred = self(X)
        return self.loss_fn_mean(pred, y)

    def validation_step(self, batch):
        X, y = batch
        with torch.no_grad():
            pred = self(X)
            loss = self.loss_fn_sum(pred, y).item()
        return loss, pred.argmax(1), y

Variante GRU : ce qui change (et seulement ca)

self.gru = nn.GRU(input_size=n_channels, hidden_size=n_hidden, batch_first=True)
...
output, h_n = self.gru(x)   # pas de cell state c_n : le GRU n'a qu'un etat cache, pas de memoire separee
last_hidden = h_n[-1]

Difference d'interface a connaitre : nn.LSTM retourne (output, (h_n, c_n)) (etat cache + etat de cellule separes), nn.GRU retourne (output, h_n) (un seul etat, qui fusionne les roles de "memoire courte" et "sortie"). Conceptuellement, le GRU fusionne les portes d'oubli/entree du LSTM en une seule porte de mise a jour, avec moins de parametres (3 matrices de poids contre 4 pour le LSTM) ⇒ plus rapide a entrainer, performance souvent comparable sur des sequences courtes/moyennes (ici 128 pas de temps).

Entrainement (Exercice 4-5), reprend MyTrainer du TP1

device = "cuda" if torch.cuda.is_available() else "cpu"
model = LSTMNetwork(n_channels=9, n_classes=6).to(device)

class Trainer:
    def __init__(self, max_epochs, device):
        self.max_epochs = max_epochs
        self.device = device

    def fit(self, model, train_dataloader, val_dataloader):
        model = model.to(self.device)
        optimizer = model.configure_optimizers()
        plotter = LiveLossPlot()   # cf. TP1 : affiche train loss / val loss / val accuracy a chaque epoch

        for epoch in range(self.max_epochs):
            model.train()
            running_loss, n_batches = 0.0, 0
            for X, y in train_dataloader:
                X, y = X.to(self.device), y.to(self.device)
                loss = model.training_step((X, y))
                optimizer.zero_grad()
                loss.backward()
                optimizer.step()
                running_loss += loss.item(); n_batches += 1
            train_loss = running_loss / n_batches

            model.eval()
            val_loss, correct, n = 0.0, 0, 0
            for X, y in val_dataloader:
                X, y = X.to(self.device), y.to(self.device)
                loss, pred, y_true = model.validation_step((X, y))
                val_loss += loss
                correct += (pred == y_true).sum().item()
                n += len(y)
            val_loss /= n
            plotter.update(epoch, train_loss, val_loss, correct / n)

trainer = Trainer(max_epochs=10, device=device)
trainer.fit(model, train_dataloader, val_dataloader)

3. Methodologie experimentale NOTE EN PHASE 1 ET 5

Comparaisons justes entre modeles

  • Memes splits train/val/test pour tous les modeles compares (meme seed de split).
  • Meme budget (nombre d'epochs ou de pas de gradient, pas seulement "meme nombre d'epochs" si les architectures different en cout par epoch).
  • Memes pretraitements (normalisation, augmentation) appliques identiquement.
  • Hyperparametres choisis sur le val set uniquement, jamais sur le test.
  • Le test set n'est regarde qu'une seule fois, a la toute fin, pour le modele final deja selectionne.

Variabilite entre runs d'entrainement

Un seul entrainement ne prouve rien : l'initialisation aleatoire des poids et l'ordre de tirage des mini-batchs font varier le resultat d'un run a l'autre. Deux consequences pratiques :

  • Fixer une seed (torch.manual_seed(...)) pour la reproductibilite locale pendant le developpement.
  • Pour comparer deux modeles serieusement, repeter l'entrainement avec plusieurs seeds et rapporter une moyenne ± ecart-type si le temps le permet ; ne jamais conclure "A meilleur que B" a partir d'un seul run si l'ecart observe est faible (potentiellement du bruit d'initialisation, pas une vraie difference de modele).

Lire une courbe train/val

Signature observeeDiagnosticPiste

Pourquoi pre-entrainer

Apprendre des representations generales sur une grande quantite de donnees (non ou faiblement supervisees), puis les reutiliser pour une tache cible ou les donnees labellisees sont rares. Exactement le raisonnement du document BERT section 5 : l'avantage du pre-entrainement est maximal quand peu de donnees labellisees sont disponibles, et diminue quand elles deviennent abondantes.

Deux strategies de fine-tuning

StrategieMecanisme PyTorchAvantageInconvenient
Feature extraction (backbone gele)for p in backbone.parameters(): p.requires_grad = False, seule la nouvelle tete entrainerapide, peu de donnees necessaires, peu de risque de sur-apprentissagele backbone ne peut pas s'adapter a la tache ⇒ plafond de performance plus bas
Fine-tuning complettous les parametres entrainables, souvent avec un learning rate plus faible que from scratchmeilleure performance si assez de donnees labelliseesplus couteux, risque d'oubli catastrophique / overfitting si trop peu de donnees

Raffinement possible : learning rate differencie par couche (plus faible pres de l'entree, plus eleve pres de la sortie), pour preserver les representations generales apprises tot tout en adaptant davantage les couches proches de la tache.
